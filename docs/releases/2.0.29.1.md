# OpenCode Front 2.0.29.1

Port revision 1 for upstream OpenCode v2.0.29, commit [`042d083`](https://github.com/anomalyco/opencode/tree/042d0832f5f3a73eaa039a58a7d565776f6d4290). The app uses version `2.0.29+1`. It connects to an existing compatible OpenCode service; the desktop archives do not bundle a backend.

## New in this release

- Install independently built frontend plugins as ZIP packages through **Settings -> Frontend plugins**, without rebuilding or redistributing the host. Packages carry a manifest with a namespaced id, version, API version, capability list, and entry assets.
- Review a package before applying it: the install preview shows the id, version, capabilities, and size, and rejects packages whose API version or capabilities are not supported.
- Enable, disable, update, and uninstall packages with isolated per-plugin storage. Updates stage the new version, activate it, and roll back the previous package and its versioned data if activation fails; uninstall can keep or delete the plugin's data, and parent/child plugin ids keep stored values separated.
- Custom panels ride the existing session Side Panel: a package registers its panel entry and content, and the host bridges it into the native "+ Add tab" menu, tab strip, layout, and session lifecycle alongside the built-in review tabs.
- Load plugin modules from stored bytes as Blob URL imports under the host CSP, sharing the host's Solid runtime with owner cleanup on disable or uninstall; hanging setups are cancelable and cannot block the manager.
- Reload in-development packages from the plugin manager without reinstalling, using a development-only refresh affordance.
- Two example packages are attached to the release as independently installable ZIPs: a session panel with a checklist, notes, and progress display, and an opt-in status footer that polls a user-supplied HTTP endpoint.

A regression introduced during this work was fixed before release: bridged panel contributions were withdrawn when the host reconciled its panel state, so clicking the menu entry did nothing. Panel and menu contributions now share a root that outlives reconciliation, and the regression is covered by tests.

## Validation

The source-boundary audit, all type checks, and 86 tests (461 assertions) passed (`bun run check`). The packaged macOS app was verified on real hardware: the release archive's Mach-O signatures were verified with `codesign --deep --strict`, the app launched a renderer helper, and an end-to-end pass installed the example panel package, connected read-only to a real local backend, and opened the plugin panel from the "+ Add tab" menu inside an actual session, with the test running under an isolated home directory. The user's real profile and backend process were not modified.

Browser fixtures use synthetic responses and mock session data where noted in the plan documents. Strict offline operation, Windows hardware, and long-running resource measurements remain unverified locally; the release workflow verifies the extracted macOS archive's signatures and renderer-helper startup before publication.

## Downloads and compatibility

The release workflow builds macOS Apple Silicon (arm64) and Windows x64 archives, plus a separate example-plugin source ZIP. Examples are not bundled into the desktop app. The macOS application is ad hoc signed and not notarized. After verifying the download, extract the archive, move `OpenCode-Front.app` to Applications, and clear quarantine before opening:

```sh
xattr -dr com.apple.quarantine "/Applications/OpenCode-Front.app"
```
